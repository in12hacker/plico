# R3.1.1 — Managed MCP Child Lifecycle

Status: DELIVERED | Base: `932a7d4` (R3.1) | Date: 2026-08-18

## P1 being fixed

`McpClient` held the server as a bare `_child: std::process::Child` with no
`Drop`, no `wait`/`try_wait`/`kill`. Rust does not reap a dropped `Child`:
after the server exited on stdin EOF it would remain a zombie until the
process ended, and every construction-failure path (`initialize`,
`tools/list`) leaked the same way. The R3.1 milestone record additionally
claimed the child "is reaped" after drop — that claim was false and is
corrected in the R3.1 record.

## Design (frozen requirements mapped)

- `ManagedChild { child: Option<Child>, graceful_timeout }` takes ownership
  immediately after `spawn` succeeds; every later `?` in `McpClient::new`
  reaps through its `Drop` backstop (requirements 1, 7).
- `shutdown_and_reap()` is the single state machine for both paths: close
  any still-held stdin (EOF), bounded `try_wait` grace (2 s production
  default, 10 ms poll), then `kill`, then always `wait` (requirements 2b–d,
  5, 6). It is idempotent (second call returns `None`).
- `Drop for McpClient` implements the order explicitly — never field-drop
  order: take the transport out of the mutex even when poisoned
  (`take_even_if_poisoned`), drop it (stdin EOF), then
  `child.shutdown_and_reap()` (requirements 2a, 3, 4). No `unwrap`, no
  panic; `ManagedChild::Drop` is the final backstop for abnormal paths.
- `transport` becomes `Mutex<Option<McpTransport>>` so the poisoned-lock
  path can still take and close it; `call_tool` (both the inherent method
  and the `ExternalToolProvider` impl) handles the taken state without
  panicking or changing the public API surface.
- No MCP wire change, no exact-14 change, no kernel change, no public API
  change, no Cargo change, no background reaper threads, no shell, no
  unbounded `wait`.

## Counterexamples delivered

| Requirement | Where | How |
|---|---|---|
| graceful EOF drop → exited and reaped | lib `managed_child_exits_gracefully_on_eof_and_is_reaped` | `cat`; outcome `ExitedDuringGrace`; `/proc/<pid>` gone (no zombie); idempotent second call |
| EOF ignored → timeout kill + wait | lib `managed_child_kills_and_reaps_when_eof_is_ignored` | `sleep 30`, 50 ms grace; outcome `KilledAfterTimeout`; `/proc` gone |
| initialize failure → no leftover child | integration `client_initialize_failure_leaves_no_zombie_children` | 25× `McpClient::new("true")` fails at handshake; zero zombies |
| tools/list failure → no leftover child | integration `client_tools_list_failure_leaves_no_zombie_children` | 25× `McpClient::new("cat")` fails at tools/list; zero zombies |
| 100× create/destroy → no zombie growth | integration `client_churn_hundred_drops_leave_no_zombie_children` | 100× real-binary client create+drop; zero zombie children |
| poisoned mutex → Drop does not panic, still reaps | lib `poisoned_transport_mutex_is_taken_without_panic` | mutex deliberately poisoned; `take_even_if_poisoned` returns the value, no panic; the reaping path uses the same helper |
| no plico-mcp residue after integration suite | `pgrep plico-mcp` after `--test mcp_test --test mcp_client_test` | zero processes, verified twice |
| external `CARGO_TARGET_DIR` stays green | acceptance commands below | both integration targets green in the external target dir |

Drop-only backstop at scale is proven by the 100× integration churn (no
explicit shutdown calls); the state-machine unit tests cover both
transitions directly.

## Test-placement note (library-suite stability)

Initial versions ran 100× churn and the construction-failure loops inside
the library suite. Every `fork` in the multithreaded test binary briefly
stalls sibling threads and trips a pre-existing, load-sensitive
flock/reopen race in the projection suite (`EAGAIN` from
`PersonalVaultStorage::open`'s non-blocking vault flock; KNOWN_ISSUES D1
family — repair is out of R3.1.1 scope, files are on the forbidden list).
Causality was bisected: with the spawn-storm tests the suite failed in
3/3 consecutive runs, with them skipped 6/6 green, baseline 932a7d4 green
throughout. The library now performs exactly two forks (one per
state-machine path) and is 8/8 green under load ~8.5; all heavy
spawn-based proofs live in the integration target, which does not co-run
with the library suite.
